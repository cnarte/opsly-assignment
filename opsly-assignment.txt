⏺ Good. Now let me propose approaches. Here are 3 architectural approaches for
  this system:

  ---
  Approach A: LangGraph Supervisor + MCP Agents (Recommended)

  How it works:
  - Each agent (Indexer, Graph Query, Code Analyst) is a standalone MCP server
  using the mcp Python SDK
  - The Orchestrator is a LangGraph StateGraph with a supervisor node that
  routes to agents via langchain-mcp-adapters
  - GitNexus handles initial repo indexing, with a sync layer that mirrors data
  into Neo4j
  - FastAPI gateway wraps the LangGraph orchestrator
  - OpenRouter via langchain-openrouter for all LLM calls (configurable model,
  default qwen/qwen3.6-plus:free)
  - Redis for conversation memory + response caching

  Pros: LangGraph handles routing, parallel execution, state management out of
  the box. MCP agents are truly independent servers. Clean separation of
  concerns.
  Cons: More dependencies (LangGraph, langchain ecosystem). Slightly higher
  complexity.

  ---
  Approach B: Pure MCP with Custom Orchestrator

  How it works:
  - All 4 agents are MCP servers
  - Orchestrator is also an MCP server but internally uses MCP client to call
  other agents
  - Custom routing logic (no LangGraph) — just async Python with the MCP client
  SDK
  - Same GitNexus + Neo4j sync, same Redis for memory

  Pros: Fewer dependencies, pure MCP architecture. Simpler to explain in a
  walkthrough.
  Cons: Must build routing, state management, parallel execution manually. More
  boilerplate.

  ---
  Approach C: LangGraph-Only (No MCP)

  How it works:
  - All agents are LangGraph nodes in a single graph, not separate MCP servers
  - Tools are registered directly as LangGraph tools
  - Simpler deployment (single process)

  Pros: Simplest architecture. Easy to debug.
  Cons: Doesn't meet the assignment requirement — the assignment explicitly
  requires MCP servers. Agents aren't truly independent.

  ---
  My recommendation: Approach A. It satisfies the MCP requirement, leverages
  LangGraph for the hard orchestration problems, and uses GitNexus as a
  productivity multiplier for indexing.

⏺ Great research. Here's what I found about GitNexus's capabilities:

  GitNexus query capabilities are strong:
  - 17 MCP tools including query (hybrid search), context (360-degree symbol
  view), impact (blast radius), cypher (raw Cypher queries)
  - Can answer "what inherits from X", "what does Y depend on", "trace imports"
  via cypher or context tools
  - Supports Cypher syntax (via LadybugDB, not Neo4j)

  GitNexus does NOT integrate with Neo4j:
  - No export, no config option to swap backing store
  - LadybugDB is deeply baked in
  - However, it generates CSV files during indexing that could theoretically be
  imported into Neo4j

  Schema coverage is good but not 100%:
  - Missing: Parameter as a node (stored as property), Docstring as a node
  (stored as property), HAS_PARAMETER and DOCUMENTED_BY relationships
  - Has everything else the assignment needs

  Revised architecture recommendation:

  Given GitNexus's strong query tools, here's a cleaner approach:

  1. Use GitNexus as the primary indexing + query engine — its query, context,
  cypher, impact tools handle most of what the Graph Query Agent needs
  2. Add a Neo4j sync layer — after GitNexus indexes, parse its CSV outputs and
  load into Neo4j with the assignment's required schema (adding Parameter,
  Docstring nodes and missing relationships)
  3. Graph Query Agent queries Neo4j for assignment-required queries, but can
  also delegate to GitNexus for richer queries (hybrid search, impact analysis)

  This gives you the best of both worlds — GitNexus's powerful indexing + the
  assignment's Neo4j requirement.
